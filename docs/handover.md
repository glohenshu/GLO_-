# 新連載作成アシスタント Ver.1 引継ぎメモ

**更新日：2026/08/18**

## 1. 概要

GLOの新規連載登録時に必要な情報を、カテゴリコードを起点に自動取得・整形する社内ツール。

本番URL：

`https://shinrensai-assistant.vercel.app/`

カテゴリコード（例：`gr1966`）を入力して「情報取得」を押すと、主に以下から情報を取得する。

| 取得元 | 用途 |
|---|---|
| kintone「GLO連載情報」 | 書籍タイトル、カテゴリID、制作No.、第1回配信日時、出版実績URL |
| 出版実績ページ | 著者紹介、内容紹介、ISBN、判型、出版年月日、カテゴリ説明用キャッチ |
| Googleスプレッドシート「毎月の記事下リンク」 | 本文テンプレート末尾HTML |
| Vercel環境変数 | 記事下リンク確認URL、MediaWeaver確認URL等 |

kintoneではカテゴリIDを完全一致で検索し、レコードに登録されている「出版実績URL」を直接利用する。

## 3. ここまで対応済み

### API処理順の修正

一時期、kintone取得直後に `res.status(200).json(result)` を返してしまい、出版実績とスプレッドシートが常に未取得になる問題があった。

現在は以下の順に修正済み。

```text
kintone
↓
出版実績
↓
記事下リンク
↓
確認用リンク生成
↓
JSON返却
```

### kintone直リンク

取得した `$id` を使って、該当レコードへの直リンクを生成するようにした。

```text
/k/{APP_ID}/show#record={recordId}
```

### 記事下リンクURL

`ARTICLE_SHEET_URL` は以下どちらでも使用可能。

- Googleスプレッドシートの完全URL
- スプレッドシートIDのみ

IDのみの場合は、アプリ側でGoogleスプレッドシートURLへ変換する。

### 著者名の誤判定対策

以前、著者紹介本文の以下のような行が著者名として誤認される問題があった。

```text
1985年 バングラデシュ正規派遣（専門：ハンセン病 ハンセン病外科）
```

現在は著者名行について、

- `名前（かな）` 形式
- 名前先頭が数字ではない
- 括弧内がひらがな・カタカナ等で構成されている
- 異常に長い文字列ではない

という条件で判定するように変更済み。

### サマリー本文

「④サマリー作成」の本文（編集用）は、内容紹介から**改行・空行を削除して一続きの文章として表示**するよう変更済み。

出典文の著者名については半角スペースを除去している。

### 本文テンプレート

記事下リンク表C列のHTML内プレースホルダーを置換するよう対応済み。

カテゴリID：

```text
grxxxx
gr●●●●
```

書籍タイトル：

```text
xxxxxxxx
●●●●●●●●
```

タイトル自体に `『』` が付いている場合は、テンプレート側の `『』` と二重にならないよう除去する。

### 4-1. カテゴリ説明の取得方法

従来は、カテゴリ説明用キャッチを探す際にkintoneの書籍タイトルを出版実績ページ本文から検索していた。

この方式だと、

```text
kintone：
「共感と信頼のサステナ経営」

出版実績ページ：
共感と信頼のサステナ経営
```

のように括弧の有無が違うだけで取得失敗する。

現在の方針は以下。

```text
カテゴリID
↓
kintoneレコード
↓
登録済み出版実績URL
↓
そのページ自身の <h1>
↓
h1直後からキャッチを抽出
```

**タイトル部分一致で出版実績を探すことはしない。**

出版実績ページ自体はkintoneに登録済みのURLで確定し、ページ内解析のみ `<h1>` を基準にする。

この方式の `fetch-info.js` 修正版は作成済み。  
**→ 2026/08/18、push済み・本番動作確認まで完了。**

- 実装コミット：`e1ffc95 Use publication h1 for catch copy`
- `main` と `origin/main` は同一（未pushの差分なし）
- 実装箇所：`api/fetch-info.js` の `extractMainH1()` と `parsePublicationPage()` 内のキャッチ抽出

### 4-2. 書籍登録「紹介文」の `<br>` 二重問題

現在、②書籍登録の紹介文は元の内容紹介を改行ごとに `<br>` へ変換している。

元データに空行がある場合、

```html
文章1<br>
<br>
文章2<br>
<br>
文章3
```

となる。

希望仕様：

```html
文章1<br>
文章2<br>
文章3
```

対応案：

```js
function textToBrCompact(text) {
  const lines = String(text || '')
    .replace(/\r\n?/g, '\n')
    .split('\n')
    .filter((line) => line.trim() !== '');

  return lines.join('<br>\n');
}
```

書籍登録の紹介文だけ `textToBrCompact()` を使用する。

著者紹介は別ルールのため、既存 `textToBr()` は残す。

**→ 2026/08/18、反映・確認まで完了。**

- `app.js` に `textToBrCompact()` を実装済み
- `BOOK_FIELD_DEFS` の `intro`（紹介文）にのみ適用済み  
  `{ key: 'intro', label: '紹介文', textarea: true, calc: () => textToBrCompact(state.pub?.intro || '') }`
- 著者紹介側は既存 `textToBr()` のまま（変更なし）
- 本番配信中の `app.js` がローカルの `app.js` と完全一致することを確認済み

検証：`gr1966` の内容紹介は実データに空行が3か所ある。  
この入力で出力が `<br>` 1つ区切りになり、`<br><br>` が発生しないことを確認した。

**1. 判型に「出版年月日」が混入（39件）**

正規表現 `/判型[：:\s]*([^\n]+)/` の `\s` が改行を含むため、判型が空欄の
ページ（電子書籍のみの作品）でラベルを飛び越えて次行「出版年月日」を拾っていた。

```text
ISBN
判型          ← 値が空
出版年月日     ← これを判型の値として取得してしまう
2026/7/31
```

②書籍登録の「判型」欄に `出版年月日` と入るため、そのまま貼ると誤登録になる。

**⚠️ 今後ここを触るときの注意：`出版年月日` の取得は同じ「改行またぎ」に
依存して正しく動いている**（ラベルの次行が値）。改行またぎを単純に禁止すると
出版年月日が壊れる。そのため修正は「改行またぎは残したまま、
取得値が既知のラベルなら空にする」方式にしてある（`FIELD_LABELS_RE`）。

**2. 著者名検出0（12件）**

例：`gr1868`（えんどう としこ）／`gr1879`（いつむ）／`gr1966`（ふらり）

`名前（かな）` 形式でないペンネームは検出されず、フォールバックが
ブロック全体を著者紹介に入れるため、**著者名・かなが空欄になり、
紹介文の先頭に名前が残っていた**。②の「著者」「表示用著者名」も空になる。

修正後は、名前行が1件も見つからない場合に限り
先頭行を著者名・以降を著者紹介として分離する（かなは空のまま手入力）。

判定は「先頭行が40字以内かつ数字始まりでない」こと。
行数は条件にしていない（`gr1764` のように経歴が無く名前1行だけのページがあるため）。
数字始まりの散文だけのブロックは従来どおり著者名にせず、全文を著者紹介に入れる。

なお `gr1949` は `長谷川 潔（はせがわ きよし）（本名：清）` と括弧が2つ連なるため
かな判定に通らず、このフォールバック経由で**全体が著者名欄に入る**。
空欄よりはましだが、手で整える必要がある。

**3. 著者名が半角括弧（2件）**

該当：`gr1866`（`夕凪 丹麗(ゆうな あかり)`）／`gr1712`（`輪月 舟(わづき しゅう)`）。
`parseNameLine` が全角 `（）` のみ対応だったため検出できなかった。

**4. `■著者略歴`（1件）**

### 5-2. 2026/08/18 記事下リンクの期間判定・年またぎ検証

本番APIが返す実シート（77行）を使い、`findSheetRow()` を配信日ごとに実行して検証した。

#### ✅ 年またぎは元から正常だった

シート37行目が年またぎ週 `12月第五週 12/28（日）～1/3（土）`。
配信日 2025/12/28・12/29・12/31・2026/1/1・1/2・1/3 のすべてで
この行に正しく一致し、期間も 2025/12/28〜2026/1/3 と正しく解決された。
2025/12/27 は前週、2026/1/4 は翌週へ正しく切り替わる。**修正不要だった。**

#### ❌ 代わりに見つかった不具合（修正済み）

**1. 期間表記の3形式のうち2形式が解析できず、行が丸ごと無視されていた**

B列には3つの表記が混在している。

```text
8/23（日）〜8/29（土）   終了側に月あり
6/1（日）～7（土）       終了側は日のみ
4/1～15                  曜日なし・終了側は日のみ
```

旧実装は `M/D` を2組探す方式だったため、下2つは**1組しか見つからず `null` を返して行ごとスキップ**していた。
77行中8行が該当。さらに波ダッシュは `～`(U+FF5E) と `〜`(U+301C) が混在している。

**2. 別の年の同じ週にマッチして、古いC列HTMLを黙って返していた** ← 影響大

シートには**1年以上分（2025年4月〜2026年10月）の行が積み上がっている**が、
B列に年は書かれていない。旧実装は全行を配信年とみなしていたため、
正しい行が上記1で解析できないと、下から探して**別の年の同じ週の行**に一致していた。

| 配信日 | 修正前 | 修正後 |
|---|---|---|
| 2025/4/5 | 2026年の「4月第二週」にマッチ | 2025年の「4月(前半)」 |
| 2025/6/10 | 2026年の「6月第二週」にマッチ | 2025年の「6月　第二週」 |
| 2027/1/5 | 2026年の「1月第二週」にマッチ | **該当なし**（手入力欄） |

特に3件目が危険で、**シートが未更新のまま年が変わると、前年のリンクを黙って貼ってしまう**。

#### 修正内容（`app.js`）

- `parsePeriodParts()` — 3形式すべてに対応。`/` を含む行を対象にし、終了側の月が省略なら開始月を使う
- `assignRowYears()` — 行ごとの実際の年を推定。最終行から上へ走査し、月が巻き戻ったら年を1つ戻す
- **年の確定はB列の曜日で採点する。** 「今日に最も近い年」だけで決めると、
  シートが6か月以上更新されないと1年ずれる（実測で確認）。曜日は年を一意に特定できるため、
  曜日一致数が最大になる年を採用し、同点のときだけ今日に近い年を使う
- 該当行が無いときは黙って別の行を使わず「該当期間が見つかりません」＋手入力欄

### 6-1. 2026/08/18 UI改修の実施内容

上表のうち、**5タブの構成と順番は変えずに**、それ以外を実施した。
`index.html` と `app.js` の構造は原則そのままで、`style.css` の差し替えが中心。

#### 上表への対応状況

| 項目 | 状態 |
|---|---|
| 上部に情報が集中している | ✅ 固定するのをタブだけにした（下記） |
| 確認リンク | ✅ 折りたたみのまま維持 |
| 解析デバッグ | ✅ `?debug=1` のときだけ表示（§7参照） |
| 5タブ | ⬜ 順番・構成は変更なし |
| コピー操作 | ✅ コピー済みに印が残る／一覧では静かに、行に触れると立つ |
| 長いtextarea | ⬜ 高さの自動調整は未着手 |
| 取得成功／失敗表示 | ✅ 空欄の理由を欄自体に出すようにした |

#### 上部固定の縮小

上部を丸ごと `position: sticky` にしていたため、**画面の41%を占めていた**（実測298px／720px）。
固定するのを**タブだけ**に変え、基本情報と検索行はスクロールで送れるようにした。

| | 変更前 | 変更後 |
|---|---|---|
| スクロール後に残る高さ | 298px（41.4%） | **42px（5.8%）** |
| 基本情報の高さ | 101px | 67px |

#### 数値の統一

改修前は**文字サイズ12種・余白19種**が混在していた。これが雑然として見える主因だった。

- 文字は5段（11 / 12 / 13 / 15 / 18px）の変数のみ
- 余白は4pxの倍数（4 / 8 / 12 / 16 / 24 / 32px）の変数のみ
- 直値は光学調整の2箇所だけ残し、理由をコメントに書いた

#### 書籍登録を「表」として読ませる

8項目の入力欄の枠を**既定で消した**。枠が8つ縦に並ぶと入力画面に見えるが、
実際は読んでコピーするだけの表なので、値そのものを読ませる。
行に触れる／書き込むときだけ枠が出るので、編集できることは失われない。
**空欄の警告（橙）は触れていなくても出したまま**にしてある。見落とすと困るため。

#### 配色・質感

- 地（机 `#EBEEE9`）・紙（`#FFFFFF`）・罫の3層を明確にした
- 罫線は `rgba` にして、どの地の上でも同じ濃さに見えるようにした
- 影は1種類だけ。浮かせるのは著者カードのみ
- 緑を `#1B6B52` → `#14684E` とわずかに深くした

#### 日本語の折り返し

タブ説明が `max-width` で絞られており、**「編集してくださ／い。」のように
語の途中で折れていた**。幅を絞るのをやめ、4タブとも1行に収めた
（最長705px、本文幅872px、**ウィンドウ幅753px以上で1行**）。

狭い画面で折り返す場合に備えて、以下を指定してある。

```css
word-break: auto-phrase;   /* 文節で折る */
line-break: strict;        /* 行頭に小書き仮名・句読点を置かない */
```

`text-wrap: pretty` と `balance` も試したが、実測でどちらも悪化したため採用しなかった
（`pretty` は「必要に／応じて」と慣用句を割り、`balance` は「削除・／修正して」と中黒直後で切る）。

#### CSSを触るときの決まり

**画面に文言・記号・状態表示を足さない。** 配色・余白・字組み・罫線・サイズのみ。
一度 `content:` で「自動生成」「編集できます」といった札を付けたが、
**仕様書にない表示**だったため取り消した経緯がある。

目視では見落とすため、検査スクリプトを通してからpushすること。確認する内容は次の4点。

1. `content:` で文言・記号を足していないか
2. 空欄の強調（`:placeholder-shown`）が合意した欄だけか
   （SNSのURL・その他リンク・コンテスト名は**空でも異常ではない**ので対象外）
3. `prefers-color-scheme` 等、環境で見た目が変わる指定を足していないか
4. `index.html` / `app.js` に実在しないクラスを狙っていないか

あわせて、**日本語が入る要素に等幅を当てていないか**（`--mono` に日本語グリフが無く
字形と字幅がばらつく）と、**コントラスト比が4.5以上か**も確認する。
